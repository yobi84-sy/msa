# 1차 설치 후: 경보·주문 알림 준비

현재 1차의 상품·회원·주문 소스는 수정하지 않는다. 주문 알림은 통합본 `patches`의 adidas mall 패치와 이후 두 패치에 포함한다.

## 적용 순서

1. 새 GUI에서 **설치**를 실행한다. 기존 1차 앱 설치·접속 검증 후 **운영 알림 구성까지 이어서 실행**한다. 별도 알림 구성 버튼을 매번 누르지 않는다.
2. 설치와 알림의 저장된 Terraform 계획은 각각 확인하고 승인한다. 인프라·호출·메트릭·로그·SMS 비용 또는 크레딧 사용이 발생할 수 있다.
3. 설치에 이어지는 알림 구성에서는 `ALERTS`·모니터링 `PUSH`를 중복 요청하지 않는다. 독립적으로 **알림 구성** 버튼을 실행하면 기존 승인 절차를 사용한다.
4. **장애 알림용 및 새 주문 알림용 이메일 구독 확인 메일**을 각각 승인한다. 확인 전에도 서비스·알림 리소스 설치는 완료될 수 있으며 GUI는 **이메일 확인 대기**로 구분한다.
5. GUI에서 `adidas-mall-upgrade` 패치를 선택한다. 주문 알림 구성과 이메일 승인을 검사한다. DB 스냅샷 후 V3.1 알림 대기열을 추가하며 기존 주문은 발송 대상으로 만들지 않는다.
6. 테스트 주문 한 건 → 주문 번호와 이메일·SMS를 비교한다. 실제 문자 비용이 발생할 수 있다.

알림 단계가 실패하면 서비스 설치 성공은 유지하고 **서비스 설치 완료 · 알림 구성 미완료**로 표시한다. 원인을 확인한 후 **알림 구성** 버튼으로 재시도한다. 검증된 SMS 샌드박스 번호가 없으면 이메일 중심으로 설치하며 SMS는 비활성화한다. 여러 확인 번호가 있으면 임의로 고르지 않고 중단한다.

## 수신자와 권한

- 이메일은 Git에서 제외한 `.yobi-local/operator-settings.json`에서 읽는다.
- SMS는 해당 서울 리전 계정에 **확인된 샌드박스 번호가 정확히 하나**일 때만 선택한다. 여러 번호면 추측해서 발송하지 않는다.
- 고객에게 자동 발송하지 않는 **관리자 알림**이다. 알림 본문에는 고객 이름·이메일·주소·전화번호를 넣지 않는다.
- 두 주문 SNS 주제와 장애 알림 주제를 분리한다. 주문 앱 IRSA는 두 주문 주제에만, Alertmanager는 장애 주제에만 Publish할 수 있다.
- 전화번호는 Terraform 민감 변수로 전달하며 코드·Git에 저장하지 않는다. 수신 정보가 들어가는 전용 Terraform state/plan은 기존 Git 제외 규칙을 적용한다.

## 경보 기준

| 항목 | 조건·경로 |
|---|---|
| 외부 HTTPS/API | EKS 외부 Lambda가 1분마다 두 URL 검사, 3회 연속 실패 또는 메트릭 누락 → CloudWatch → 기존 SNS 이메일 |
| 앱 가용성 | soldesk의 서비스 정상 Deployment 복제본 0이 2분 지속 |
| Pod 재시작 | 10분 동안 3회 이상, 1분 지속 |
| RDS CPU | 기존 80%·5분 평균·3구간 유지, 정상 복구 이메일도 연결 |
| RDS 저장 공간 | 실제 할당 공간의 20% 미만이 5분 지속 |
| RDS 메모리 | FreeableMemory 128MiB 미만이 5분 지속; micro DB의 시작값이며 정상 기준선을 보고 재조정 |
| 노드 | Ready 아님 3분 / 메모리 90% 초과 5분 |
| Argo | 동기화 불일치·비정상 또는 장기 Progressing이 5분 지속 |
| 확장 한계 | HPA desired가 max 도달 / 노드 그룹의 확인된 maxSize 도달이 5분 지속 |
| 알림 전송 장애 | 주문 발행 실패 카운터 증가 또는 상태 수집기 중단 |

Prometheus 경보는 Alertmanager에서 묶고 최초 30초 대기, 그룹 간격 5분, 지속 경보 재알림 30분, 정상 복구도 이메일로 보낸다. CloudWatch는 별도 상태 변화 알림 경로이며 이 재알림 주기를 그대로 적용하지 않는다.

## 주문 처리 보장과 한계

- 주문·재고 변경과 EMAIL/SMS 대기열 INSERT는 같은 DB 트랜잭션이다. 롤백하면 알림도 남지 않는다.
- 같은 주문 요청 키를 재전송해도 알림 행은 새로 만들지 않는다.
- 별도 발송기가 커밋된 행만 처리하고 일시 실패는 지수 지연 후 최대 5회 시도한다. 발송 실패가 완료된 주문을 취소하지 않는다.
- SMS는 **UTC 기준 하루 10회 애플리케이션 발행 시도**로 제한한다. 실패 시도도 포함한다. 한도 초과 행은 다음 UTC 날짜로 연기한다. 모든 AWS SMS에 대한 계정 차원의 강제 비용 상한은 아니다.
- SNS 일반 주제이므로 전달은 **최소 1회** 방식이다. SNS 수락 직후 프로세스 장애가 생기면 재시도로 중복 문자가 갈 수 있다. 정확히 한 번 전달이나 휴대전화 도착까지 보장한다고 주장하지 않는다.
- DB `order_notification_outbox`의 SENT는 SNS가 발행을 수락했다는 뜻이다. 실제 수신은 메일함·전화에서 검증한다.

## 검증

기본 실행은 계획만 출력한다. 실제 부하 시 `--execute`와 `LOAD` 확인이 필요하다.

```powershell
python operations/notifications/load_test.py --mode http --duration 300 --workers 2
python operations/notifications/load_test.py --mode cpu --duration 600 --workers 6
python operations/notifications/load_test.py --mode rds --duration 1080 --workers 2
```

HTTP는 작업자당 최대 초당 5회, CPU는 최대 6개 Pod·각 1 CPU 상한·최대 10분이다. 실제 부하가 HPA/노드 확장을 유발하면 비용이 늘 수 있다. 기존 HPA나 노드 최대치는 바꾸지 않는다. CPU 테스트는 노드별 한 Pod로 배치해 확장을 유도하고 본인 Job UID를 확인해 정리한다. HTTP 테스트와 CPU 테스트가 반드시 모든 경보를 발생시키는 것은 아니다. 실제 메일 수신과 정상 복구를 기록한다.

RDS 모드는 최대 두 연결에서 상수의 SHA2를 계산하는 읽기 전용 BENCHMARK를 반복한다. 주문·회원·재고를 수정하지 않는다. 현재 15분 CPU 조건을 평가할 시간을 확보하려면 18분 예시를 사용한다(최대 20분). 서비스 응답 저하와 DB CPU 크레딧 비용이 생길 수 있으므로 실제 실행을 별도로 승인한다. 부하가 목표 CPU에 도달하거나 메일이 도착한다고 미리 보장하지 않는다.

전체 삭제 시 GUI는 데이터 백업 후 **추가 알림 Terraform 삭제 계획을 별도 승인**받고 EKS/RDS 삭제 전에 Lambda·스케줄·SNS·IRSA·추가 경보를 정리한다. 전용 state를 임의로 지우거나 폴더를 옮겨 분실하지 않는다.

## 현재 검증 범위

로컬 주문/재시도/문자 한도 테스트, 실제 로컬 MySQL 마이그레이션, Promtool 경보 발생·해제, Alertmanager 설정 및 Terraform validate를 수행한다. 실제 알림 인프라 적용·주문 문자 발송·CPU/HTTP 부하 검증은 별도 실행 단계다. Grafana SSA 복구 두 파일만 GitHub에 반영했다.
